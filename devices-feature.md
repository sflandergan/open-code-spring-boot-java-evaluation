# Device Management Feature Implementation Plan

## 1. Overview
Implement a new feature to manage devices via a RESTful API.  
Key capabilities:
- Create, Read, Update, and Delete devices.
- Assign sensors to devices using an idempotent PUT operation.

## 2. API Specification
| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/api/devices` | Create a new device. |
| `PUT`  | `/api/devices/{id}/sensors` | Assign one or more sensors to a device (idempotent). |
| `GET`  | `/api/devices` | Retrieve all devices. |
| `GET`  | `/api/devices/{id}` | Retrieve a device by its identifier. |
| `PUT`  | `/api/devices/{id}` | Update device details (name, description). |
| `DELETE`| `/api/devices/{id}` | Delete a device. |

## 3. Domain Model
### `Device`
- `id`: Long (auto‑generated)
- `name`: String
- `description`: String

### Relationships
- A device can have multiple sensors.
- Sensors are referenced by their IDs (many‑to‑many relationship).

## 4. Persistence
- **Database Table**: `device` with columns `id`, `name`, `description`.
- **Junction Table** (if needed): `device_sensor` linking device IDs to sensor IDs.
- Use Flyway migration script to create/upgrade schema.

## 5. Service Layer
Create `DeviceService` in package `de.sfl.devices` with the following methods:
```java
Device createDevice(CreateDeviceRequest request);
Device getDeviceById(Long id);
List<Device> getAllDevices();
Device updateDevice(Long id, UpdateDeviceRequest request);
void deleteDevice(Long id);
Device assignSensors(Long deviceId, Set<Long> sensorIds); // idempotent
```

## 6. Controllers
- `DeviceController` in package `de.sfl.devices.web`.
- Map request DTOs to entities and delegate to `DeviceService`.
- Return appropriate HTTP status codes (201 Created, 200 OK, 404 Not Found, 409 Conflict, etc.).

## 7. Data Transfer Objects (DTOs)
- `CreateDeviceRequest`
- `UpdateDeviceRequest`
- `SensorAssignmentRequest` (contains a set of sensor IDs)
- Mapper methods to convert DTO ↔︎ Entity.

## 8. Validation
- Use Bean Validation (`@NotBlank`, `@Size`) on request fields.
- Return `400 Bad Request` with validation errors if payload is invalid.

## 9. Security & Error Handling
- Apply Spring Security to restrict access as needed.
- Centralized `@ControllerAdvice` for handling:
  - `DeviceNotFoundException` → 404
  - Duplicate device name → 409
  - Validation errors → 400

## 10. Testing Strategy
- **Unit Tests**: Service layer with Mockito mocks.
- **Controller Tests**: Spring Boot `@WebMvcTest` using `MockMvc`.
- **Integration Tests**: Use `@SpringBootTest` with an in‑memory database; verify idempotent sensor assignment.
- **Repository Tests**: Extend `RepositoryIT` base class; verify schema generation.

## 13. Acceptance Criteria
- All API endpoints respond correctly according to the specification.
- Sensor assignment operation is idempotent (re‑assigning the same sensor set does not create duplicates).
- Existing unit and integration test suites pass.
- Documentation generated by Springdoc OpenAPI reflects the new endpoints.
